# XH-202620 榜题分析报告

## 概述

这个榜题要做的不是一篇“AI赋能教育”的策划书，也不是一个只会聊天的通用问答机器人，而是：**选择一个具体高等教育学科和一个真实教学/科研痛点，基于大模型、学科知识库和任务工作流，做出可在线体验、可复现、可追溯、经过真实用户验证的学科垂类智能应用。**

对教育技术学研究生而言，最适合从教育技术学中的真实任务入手，例如研究设计、教学设计评审、学习分析与干预，而不是泛泛做“教育大模型”。

## 一、主办方实际上要求做什么

作品必须同时具备以下四层：

1. **明确的学科范围**：例如教育技术学，而不是笼统的“教育”。还可继续缩小到学习分析、教学系统设计、在线学习、教师数字素养等方向。
2. **真实且具体的场景**：从助教、助学、助研中选一个主场景，解决一个高频、高耗时、易出错或难以个性化的问题。
3. **能实际运行的智能应用**：需要有 Demo 地址，能够从用户输入到结果输出完整运行，不是概念原型或 PPT 动画。
4. **可验证的效果**：至少 3 个典型问题的准确性论证，至少 2 名真实目标用户的试用记录，并有质量、效率或一致性的量化证据。

赛题允许使用讯飞星火或其他开源大模型，也允许使用赛事推荐平台或其他工具。原文把知识库、LoRA/SFT 微调、RAG、工作流、多模态和场景化开发列为“技术实现建议”，因此：

- **不要求从零训练一个基础大模型**；
- **模型微调不是硬性要求**；
- 采用“成熟大模型 + 高质量学科知识库 + RAG + 专业工作流 + 工具调用”即可形成垂类应用；
- 但只有“上传资料后聊天”的普通 RAG 问答，技术实现度和创新性通常不够。

## 二、硬性功能门槛

应用至少必须满足原文第 1—4 项基础功能：

1. **贴合真实场景**：围绕具体学科痛点设计，输出符合学科规范。
2. **自然多轮交互**：支持自然语言任务、上下文理解、歧义消解和连续对话。
3. **知识权威可信**：建立高质量、结构化、准确且及时的领域知识。
4. **内容可追溯**：涉及官方、政府或权威内容时，准确引用并标注来源。

建议再至少实现两项创新功能，优先顺序为：

- 复杂问题求解：把专业任务拆成可审查的步骤；
- 个性化与自适应：根据用户水平、历史任务或偏好调整输出；
- 可复制推广：可以迁移到多门课程或多所高校；
- 多元生成：既遵循规范，又允许用户配置目标、模板和表达方式。

## 三、最终应呈现出什么结果

### 1. 用户看到的产品结果

应当是一个可访问的网页或应用，而不是单个聊天窗口。较完整的产品界面应包含：

- 用户身份、任务和目标设置；
- 材料上传或数据接入；
- 分步骤任务流程；
- 生成结果及可编辑结构化输出；
- 每个关键结论的来源引用和原文定位；
- 质量检查、风险提示或置信度提示；
- 历史记录、版本对比或个性化档案；
- 明显的“AI 生成内容”标识。

### 2. 评委看到的演示闭环

3 分钟演示视频应呈现一条完整链路：

> 真实用户任务输入 → 系统识别需求 → 调用学科知识与工具 → 分步处理 → 输出专业结果 → 展示引用依据和质量检查 → 用户采用或修订结果

评委应能迅速看明白四件事：以前怎么做、痛点是什么、系统改变了什么、效果提升了多少。

### 3. 必交材料

| 编号 | 材料 | 核心要求 |
|---|---|---|
| 01 | 参赛信息 | 报名系统审核通过且盖章的报名表，信息完全一致 |
| 02 | 伦理与安全合规性声明 | 不使用未脱敏个人数据；不伪造数据、文献；系统标注 AI 生成内容；建议签字或盖章 PDF |
| 03 | 作品 Demo | 在线体验地址和使用说明，可自行部署 |
| 04 | 作品方案 | PPT，100MB 以内；包括作品阐述、功能、技术、运行效果、迭代、创新、团队 |
| 05 | 作品代码 | 代码、模型文件或 ServiceID、技术报告，必须可复现 |
| 06 | 效果验证报告 | 至少 2 名真实目标用户；测试记录；量化效果；3 分钟以内真实交互视频 |

## 四、评分结构及应对方式

| 评分项 | 分值 | 应对重点 |
|---|---:|---|
| 创意实用度 | 20 | 问题足够具体，来自访谈或真实流程；方案不是通用聊天机器人 |
| 技术实现度 | 20 | 高质量知识库、复杂工作流、专业工具调用、完整功能闭环 |
| 内容质量度 | 20 | 专业准确、引用可核查、3 个典型案例、多轮交互流畅 |
| 作品完成度 | 10 | Demo 稳定运行，材料齐全，代码可复现，无关键故障 |
| 技术先进性 | 10 | 有明确技术增量、性能对比和迭代空间，不是简单套壳 |
| 商业化潜力 | 10 | 明确用户、推广对象、部署方式和复制路径 |
| 用户认可度 | 10 | 至少 2 名真实用户，说明身份、频次、时长、场景和效果 |

正常总分 100 分。若能提供 **50 人以上真实使用环境的用户数据与效果验证**，可酌情加分，最高加 10 分。可见赛事非常重视“真用”和“有效”，不能把全部精力放在模型技术名词上。

## 五、教育技术学方向的三个可选方案

### 方案 A：教育技术学研究设计与方法智能体（推荐）

**目标用户**：教育技术学硕士生、博士生、青年教师。

**真实痛点**：研究问题、理论框架、研究方法、测量工具、数据分析和结论之间经常不一致；研究设计检查依赖导师，耗时且反馈不系统。

**核心功能**：

- 输入研究主题、研究问题和已有方案；
- 识别研究范式与问题类型；
- 检查“问题—理论—变量—方法—数据—结论”一致性；
- 从权威方法文献和规范中给出有出处的修改建议；
- 推荐适用方法，但解释适用条件和限制；
- 生成研究设计审查报告、风险清单和修改前后对照；
- 可调用统计或代码工具验证分析方案，但禁止虚构数据和文献。

**为什么适合参赛**：学科属性强、工作流清晰、真实用户容易找到、可用专家评分一致性和任务耗时做量化验证。难点在于必须把范围限定在某类研究，例如“教育技术学量化与混合研究设计”，避免变成泛化论文助手。

### 方案 B：学习分析诊断与教学干预智能体

**目标用户**：高校课程教师、助教和学生。

**核心功能**：接入作业、测验和学习行为数据，识别知识薄弱点或学习风险，生成可解释的诊断和个性化干预方案，并追踪干预效果。

**优势**：教育技术特色最明显，量化证据强，容易体现个性化与自适应。

**主要条件**：需要获得真实课程数据、教师配合和合规授权；所有数据必须脱敏。若团队没有稳定的数据来源，不宜选择。

### 方案 C：教学设计一致性评审与改进智能体

**目标用户**：高校教师、师范生、教育技术人员。

**核心功能**：读取课程标准、教学内容和学情信息，检查“目标—活动—评价”一致性，结合教学设计理论与评价量规提出修改意见，并输出带引用的教学设计和版本对比。

**优势**：开发难度较低、用户易找、演示直观。

**风险**：同类备课工具较多，必须突出“理论驱动的一致性诊断、可解释评分、版本迭代和效果验证”，不能只做教案生成。

### 选择建议

- 能拿到真实课程行为数据：优先方案 B；
- 有教育研究方法专家和研究生用户：优先方案 A；
- 团队技术力量有限、周期紧：优先方案 C。

综合专业匹配、数据可得性和竞赛可验证性，当前最推荐 **方案 A：教育技术学研究设计与方法智能体**。

## 六、推荐方案的最小可行产品

第一版只做一个高价值闭环：**上传研究计划书 → 自动解析 → 一致性审查 → 引用证据 → 修改建议 → 生成审查报告**。

### 必做模块

1. **学科知识库**：教育研究方法教材、教育技术领域研究规范、权威期刊方法指南、常见研究设计与测量规范。每条资料保留作者、标题、年份、页码或 URL、授权状态。
2. **RAG 检索**：分段、元数据过滤、混合检索、重排序、引用定位和无证据拒答。
3. **专业工作流**：材料解析 → 研究问题分类 → 理论与变量检查 → 方法匹配 → 数据与分析检查 → 伦理风险检查 → 报告生成。
4. **规则和工具**：将量规规则程序化；必要时调用统计代码验证样本量、分析方法或指标计算。
5. **交互界面**：任务进度、分模块结果、证据来源、问题追问、结果导出、修改前后对比。
6. **安全机制**：个人数据脱敏、权限控制、日志、AI 标识、禁止伪造文献和数据、关键结论提醒人工复核。

### 不建议第一版做的事情

- 从零训练大模型；
- 一次覆盖全部教育学研究方法；
- 同时做助教、助学、助研三个大场景；
- 为了“技术先进”堆叠多智能体，却没有稳定性和效果对比；
- 自动替用户生成虚构论文、调查数据或参考文献。

## 七、效果验证应怎样设计

效果验证不能只放“用户觉得很好”的截图。建议设置人工基线和系统辅助条件，让同一批用户完成相同任务。

### 至少测六类指标

1. **任务完成率**：能否完成整条研究设计审查流程。
2. **专业准确率**：专家判断正确建议数 / 总建议数。
3. **引用正确率**：引用是否真实、相关、可定位。
4. **一致性**：系统结论与 2 名专家结论的一致程度。
5. **效率提升**：人工审查时间与系统辅助后时间的差异。
6. **用户体验**：可使用 SUS 量表或结构化问卷，并记录真实任务、使用时长和修改采用率。

### 三个典型测试案例

- 案例 1：研究问题和研究方法明显不匹配，系统能否准确识别并引用规范；
- 案例 2：变量、测量工具和数据分析存在部分缺口，系统能否分步追问和补全；
- 案例 3：开放性复杂方案，系统能否给出多个可行路径、适用边界和风险，而不是武断给出单一答案。

至少邀请 2 名真实用户满足硬门槛，建议尽量做到：2—3 名教育技术学教师或方法专家负责专业评分，10—20 名研究生参与可用性测试；如果有条件，扩展到 50 人以上争取加分。

## 八、团队和条件

### 建议团队配置

- 教育技术/研究方法负责人 1—2 人：需求、知识库、专业评价；
- 大模型/RAG 工程 1—2 人：检索、工作流、评测和安全；
- 前后端开发 1—2 人：Demo、部署、日志和数据接口；
- 用户研究与材料负责人 1 人：访谈、测试、报告、PPT 和视频。

4—6 人即可完成，不必凑满 10 人。团队最多 10 人、指导教师最多 3 人；可跨专业、跨学校、跨地域，但只能由 1 所单位作为申报主体。

### 必要资源

- 可合法使用的权威学科资料及明确的版权/授权边界；
- 至少 2 名真实目标用户，最好提前锁定专家和 50 人测试场景；
- 大模型 API 或本地模型、向量数据库、后端服务和稳定的在线部署；
- 数据脱敏、访问控制、日志和备份机制；
- 一名能把教育学指标转成可量化评测方案的成员。

## 最终判断

这道题对教育技术学研究生是匹配的，但获奖关键不是提出宏大的“AI+教育”概念，而是把教育技术学知识转成一条专业、可解释、可验证的产品工作流。建议以一个窄场景做深：**权威知识库保证可信，专业工作流体现学科性，真实用户数据证明有效，稳定 Demo 展示完成度。**
